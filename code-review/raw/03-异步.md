# 03 异步正确性评审 — nasdeck backend 0.1.0

- 评审对象：`backend/app`（fnOS NAS 硬件监控面板，FastAPI + SQLAlchemy async + aiosqlite + APScheduler 3.x + WebSocket 秒级推送）
- 评审维度：共享状态竞态、采集器生命周期、aiosqlite 并发、downsampler 数据一致性、WebSocket 背压与断线清理
- 方法：逐文件实读指定文件（cache/history/scheduler/downsampler/8 个 collector/db 4 件/realtime），并交叉实读支撑文件（system_resources、gpu、temperature、power、async_cmd、engine、fan_manager、self_test、selftest_schedule、volumes、smart_history、capacity、sync_watch、docker_watch、raid_card、hwmon_driver、api/v1/monitor、api/v1/storage、api/v1/report、main、config、pyproject.toml）。所有行号以当前工作区代码为准。
- 事实基线：pyproject.toml 锁定 `apscheduler>=3.10,<4`、`uvicorn[standard]>=0.29`（默认 websockets 实现）、`sqlalchemy[asyncio]>=2.0`、`aiosqlite>=0.20`；版本 dev-0.2.12。APScheduler 3.x 默认：`coalesce=True`、`max_instances=1`、`misfire_grace_time=1s`。
- 判定口径：asyncio 单事件循环内，get/set 之间**无 await 点**的读-改-写判为原子安全；check 与 act 之间存在 await 的才判竞态。

## 结论摘要

**P0 = 0，P1 = 3，P2 = 8。** 未发现必现数据损坏或死锁。三个 P1：降采样把"未封口的当前桶"永久冻结为部分聚合（系统性聚合失真）；smartctl 磁盘扫描存在跨长 await 的检查-执行竞态（多调用方可并发重复扫描）；`psutil.disk_usage` 同步跑在事件循环上（失联网络挂载点可冻结整个进程）。核心骨架（cache 无锁单写多读、ingest 批量写、WS 每连接独立任务、调度异常吞噬）设计上是自洽的，问题集中在"同步 IO 上循环"与"缓存窗口跨 await"两类模式。

## P1 发现

### P1-1 降采样聚合包含未封口的当前桶，`have` 查重使其永久冻结为部分均值

- **位置**：`backend/app/tasks/downsampler.py:38-41`（调用点）、`:123`（签名，仅下界）、`:136-138`（select）、`:144-146`（桶键 floor）、`:149-155`（have 查重）、`:166`（插入）
- **证据**：
  ```python
  # downsampler.py:38-39, :41
  cutoff = _iso_minutes_ago(settings.raw_keep_minutes)
  await _aggregate(db, "raw", "1m", 1, cutoff)
  await _aggregate(db, "1m", "10m", 10, _iso_minutes_ago(7 * 24 * 60))
  # downsampler.py:137
  .where(MetricPoint.granularity == from_g, MetricPoint.ts >= since)   # 只有下界，无上界
  # downsampler.py:152-155
  have = {r[0] for r in existing.all()}
  ...
      if key in have:
          continue
  ```
- **问题**：`_aggregate` 的时间窗只有下界 `ts >= since`，因此 tss 包含"当前分钟尚未写完"的 raw 行（ingest 写手 ≤2s 落库，downsample 时刻必然可见）。桶键 `_bucket_key`（:104-145）把 ts floor 到桶起点，于是"当前分钟桶"以部分行（如 60 行里的 7 行）的均值被插入 1m 表；下一轮（5 分钟后）该桶键已进入 `have` 集合被 `continue` 跳过，**永远不再修正**。1m→10m 同理且更重：10 分钟桶内第一轮 downsample（约桶开始后 0-4 分钟）就把该 10m 桶冻结，约缺失后半段 5-6 个 1m 行。
- **影响时序**：每次 downsample run 必现（非偶发）。raw 保留 120 分钟内查询走 raw 表不受影响；一旦窗口超过 raw_keep（24h/7d/30d 图表）开始读到 1m/10m 表，每分钟一个残缺 1m 桶、每个 10m 桶约一半时长缺采样，长窗口曲线出现周期性凹陷/毛刺，`stats()` 加权均值随之偏移。
- **修复建议**：给聚合加排他上界——只聚合"已封口"的桶：在插入循环里跳过 `key >= _bucket_key(当前时刻)` 的桶（最简单，且下一轮该桶在 raw 120 分钟窗口内仍可完整聚合）；或给 `_aggregate` 增加 `until` 参数在 select 上加 `ts < until`。注意修复后不要破坏迁移幂等分支（:74-85）。
- **附带（同文件断电缺口，P2）**：崩溃停机超过 raw_keep_minutes 后，上次成功聚合点之后、早于 `cutoff` 的最后 ≤5 分钟 raw（:38-39）在下次 run 被 :174 附近的 `ts < cutoff` 删除而从未进入 1m，聚合历史在崩溃点留下 ≤5 分钟缺口。属可接受的采集流丢失策略，记录在案，不计入问题计数主体（列为本条附注）。
- **优先级**：P1（必现的聚合数据失真、可由 raw 重算恢复，故不到 P0"必现数据损坏/死锁"；若项目把聚合表正确性视为硬性数据完整性强依赖，可升级 P0）。

### P1-2 `_smart_disk_scan` 检查-执行窗口跨最长 15s 的 await，多调用方并发重复扫描

- **位置**：`backend/app/services/monitor/temperature.py:134`（TTL 检查）→ `:159`（`await asyncio.gather(...)` 逐盘 smartctl，单盘 timeout 15s）→ `:170`（`_disk_cache.update`）
- **证据**：
  ```python
  # temperature.py:134
  if now - _disk_cache["ts"] < _DISK_CACHE_TTL:
      return
  # temperature.py:159
  outs = await asyncio.gather(*(_probe_disk(name, serial_hint) for ...))
  # temperature.py:170
  _disk_cache.update({...})
  ```
- **问题**：TTL 检查（:134）与缓存更新（:170）之间夹着逐盘 smartctl 探测的 gather，N 盘 × 15s 超时上限。期间检查窗口对其他协程完全敞开。
- **影响时序**：调用方共四处可并发进入——`medium_5s.py:64`（temperatures，5 秒一拍）、`slow_60s.py:74`（disk_health，60 秒一拍）、`api/v1/monitor.py:45`（/summary 的 temperatures，cache-miss 路径）、`api/v1/report.py:32`。扫描在途的 15s 内，medium_tick 还会再拍 2-3 次，每次都通过 :134 检查并各自发起整轮 N×smartctl fork → 进程风暴、5s 拍被拖长（自身超时 12s 兜底，:61-64 的 try/except 吞掉后跳过本拍）、磁盘休眠被反复打扰（`-n standby` 只保护读数据，探测本身仍 fork）。最终一致（最后写者胜），无数据损坏。
- **修复建议**：加 `asyncio.Lock`（后续调用者排队等结果）或 "scanning" in-flight 旗标（后来者直接用旧值返回）；或先 `_disk_cache.update(ts=now)` 占位、失败再回滚。
- **优先级**：P1（偶发资源放大 + 采集延迟；功能不损）。

### P1-3 `psutil.disk_usage` 同步跑在事件循环上，失联网络挂载点可冻结整个进程

- **位置**：`backend/app/tasks/collectors/volume_15m.py:28`（采集器内直接同步调用）、`backend/app/services/monitor/volumes.py:26-32`（`psutil.disk_partitions` + `psutil.disk_usage(part.mountpoint)`）、`backend/app/api/v1/storage.py:142`（async 处理器内同款调用）
- **证据**：
  ```python
  # volume_15m.py:28
  volumes = volume_service.list_volumes()          # 同步，无 to_thread
  # volumes.py:26-32
  for part in psutil.disk_partitions(all=False):
      ...
      usage = psutil.disk_usage(part.mountpoint)   # statfs，可无限期阻塞
  # storage.py:141-142（async def get_volumes 内）
  volumes = volume_service.list_volumes()
  ```
- **问题**：`list_volumes()` 是纯同步函数，在 `volume_tick`（15m 任务）与 `GET /api/v1/storage/volumes` 两个 async 上下文中直接执行。`psutil.disk_usage` 底层 statfs 对 NFS/SMB 等网络文件系统的失联硬挂载点会**无限期阻塞**（D 状态，Python 层无法超时）。
- **影响时序**：NAS 场景存在网络挂载且对端失联（掉线、断网、挂载点 stale）时：任一次 15 分钟 tick 或一次页面刷新触发 → 整个事件循环冻结 → 1s 采集停摆、全部 WS 断流、所有 API 无响应，且无任何超时兜底，直到 statfs 返回或进程重启。
- **修复建议**：两处调用包 `await asyncio.to_thread(...)`（至少不冻结循环，线程池可配超时观察）；更彻底的做法是仅对本地文件系统（fstype 白名单/`part.device` 以 `/dev/` 开头）调 disk_usage，网络挂载点跳过或改用带超时的子进程探测。
- **优先级**：P1（条件触发——需存在失联网络挂载；一旦触发为全站挂起，无自愈路径）。

### P1-4 gpu 名称解析 `run_cmd_sync("lspci")` 阻塞事件循环（一次性，最坏 10s）

- **位置**：`backend/app/services/monitor/gpu.py:338`（`run_cmd_sync("lspci", ..., timeout=10)`）、`:302`（`subprocess.Popen` 同步 spawn）、`:415`（5s 缓存检查点）；调用链 `medium_5s.py:64 → gpu.collect() → _intel_reader().ensure()`
- **证据**：
  ```python
  # gpu.py:338
  out = run_cmd_sync("lspci", "-nn", "-d", f"{vid:x}:{did:x}", timeout=10)
  ```
- **问题**：Intel GPU 首次 collect（cache miss，:415）时在事件循环上同步等待 lspci 子进程，最坏 10 秒；:302 的 Popen 惰性启动也是同步 fork（毫秒级）。
- **影响时序**：仅进程启动后第一个含 Intel GPU 的 5s 拍触发一次；期间 1s 拍跳秒、WS 断流、调度器 misfire。lspci 缺失时异常被 except 捕获回退，阻塞时长短。唯一调用方是 medium_tick（max_instances=1），:415 的 check-then-act 实际无并发对手。
- **修复建议**：改用异步 `run_cmd`（asyncio.create_subprocess_exec，项目已有封装），或预启动解析放到 lifespan 阶段。
- **优先级**：P1 下限（一次性、上限 10s，但对秒级系统而言阻塞代价高；若 lspci 在目标环境恒定存在且耗时 <1s，可降 P2）。

## P2 发现

### P2-1 `system_resources.snapshot()` 为 async 壳的全同步函数，psutil/proc 直读每秒跑在事件循环

- **位置**：`backend/app/services/monitor/system_resources.py:362`（`async def snapshot()`，函数体内零 await）、`:400`（`len(psutil.pids())`）、`:201-205`（`psutil.net_io_counters(pernic=True)`）、`:234`（`psutil.disk_io_counters`）、`:341-360`（逐核 cpu_freq 读 sysfs）；调用方 `fast_1s.py:24`（每秒）与 `api/v1/monitor.py:30、:82-87`（cache-miss 路径）
- **证据**：
  ```python
  # system_resources.py:362
  async def snapshot() -> dict:
      # 内部全部为同步 psutil / open("/proc|/sys") 调用，无一个 await
  ```
- **问题**：每秒在事件循环上执行 psutil 全家桶 + /proc//sysfs 直读。典型耗时毫秒级，但 psutil.pids() 遍历 /proc 在高进程数 NAS 上更贵；任何一次文件系统抖动都会放大为跳秒。同类：`hwmon_driver.py:70/87/101` 同步 sysfs 读写（µs 级，影响可忽略，仅记录模式）。
- **修复建议**：`await asyncio.to_thread(_snapshot_sync)`；注意 `_cpu_stat_last`、`_freq_max_mhz` 等模块级状态将变为跨线程访问，需顺带加锁或改线程局部。
- **优先级**：P2（当前实测模式风险，非现行故障）。

### P2-2 scheduler 启动不可重入；start_jobs 无幂等守卫

- **位置**：`backend/app/tasks/scheduler.py:28`（模块级单例 `AsyncIOScheduler`）、`:31-45`（`start_jobs`，add_job 无 `replace_existing=True`，仅 :50 `if not scheduler.get_jobs()` 粗防）、`:52`（`scheduler.start()` 无 running 保护）
- **证据**：
  ```python
  # scheduler.py:52
  scheduler.start()          # APScheduler 3.x 对已运行实例再 start 抛 SchedulerAlreadyRunningError
  ```
- **问题**：生产单进程 lifespan 只走一次无碍；但同进程二次 startup（测试、嵌入、热重载）会抛异常。`start_jobs` 可被绕过 start() 直接调用（`tests/test_selftest_schedule.py:134` 实际直调），对已注册 id 重复 add_job 抛 ConflictingIdError。
- **修复建议**：`if scheduler.running: return`；add_job 统一加 `replace_existing=True`。
- **优先级**：P2。

### P2-3 shutdown(wait=False) 不管控在途 job；downsample job 缺显式 coalesce（默认行为等价）

- **位置**：`backend/app/tasks/scheduler.py:62`（`scheduler.shutdown(wait=wait)`，main.py:74 传 False）、`:42`（downsample job 未写 `coalesce=True`，其余 8 个 job 均显式写了）
- **问题**：AsyncIOScheduler 3.x 下 wait=False 不等待/不取消在途协程 job，lifespan 随后的 ingest.stop() 与循环关闭可能在 job 仍持 DB 会话时发生（关闭期偶发 pending-destroy 警告）。:42 依赖 APScheduler 3.x 默认 `coalesce=True` 兜底，与代码注释宣称的"全部显式"不一致，行为无差。
- **修复建议**：downsample 补 `coalesce=True` 保持一致；关闭路径可接受现状，或在 shutdown 前对已知长任务做一次协作式取消。
- **优先级**：P2。

### P2-4 ingest 写手协程无 done-callback，意外死亡静默；批量落库失败整批丢弃

- **位置**：`backend/app/db/ingest.py:117`（`_task = asyncio.create_task(_run(), name="ingest-writer")`，无 add_done_callback）、`:68-73`（队列满丢行+限频日志）、`:84-96`（`_write` executemany，异常捕获后整批放弃）
- **证据**：
  ```python
  # ingest.py:117
  _task = asyncio.create_task(_run(), name="ingest-writer")
  # ingest.py:92-96（_write 内 except 捕获全部异常，仅 debug 日志，批次丢失）
  ```
- **问题**：写手是全系统唯一落库通道，若 `_run` 出现未捕获异常（当前逻辑看被 _write 的 except 全覆盖，属防御缺失而非现行 bug）将静默死亡，submit 继续入队直至队列满丢数据。busy_timeout=3000 超时后 database is locked 时整批 ≤50 行丢弃（采集流按设计可丢，含一轮 hardware 快照）。
- **修复建议**：`_task.add_done_callback` 记录异常并告警（可选自动重建写手）；locked 时可重试一次再放弃。
- **优先级**：P2。

### P2-5 WS 单连接无 send 超时/上限，慢客户端连接可长期滞留

- **位置**：`backend/app/api/ws/realtime.py:112-115`（循环 `await ws.send_text(...)` + `await asyncio.sleep(1)`）、`:96-97`（recv 侧断连置 stop）、`:151-158`（finally 取消任务并 gather）
- **证据**：
  ```python
  # realtime.py:112-115
  await ws.send_text(snap_text)
  ...
  await asyncio.sleep(1)
  ```
- **问题**：每连接独立任务、无共享连接集（天然无广播并发修改问题，见"未发现"节）。uvicorn[standard] 的 websockets 实现 send 有流控背压，缓冲有界，不会内存爆炸；但 TCP 半开/慢客户端时 send 可无限期挂起，该连接与其推送任务滞留直至对端超时，无主动清理。`_last_snap_text`（:41-44）单循环内复用，安全。
- **修复建议**：`await asyncio.wait_for(ws.send_text(...), timeout=N)`，超时主动 close 走 finally 清理。
- **优先级**：P2。

### P2-6 SQLite 多写者依赖 WAL+busy_timeout 兜底；连接池上限未显式；selftest 会话跨数小时

- **位置**：`backend/app/db/session.py:16-17`（全局 engine 单例，未显式配置 pool → 默认 AsyncAdaptedQueuePool，上限约 5+10）、`:38/:40`（WAL、busy_timeout=3000 每连接设置）、`backend/app/tasks/selftest_schedule.py:232-243`（巡检自建会话跨 `asyncio.sleep(15)` 循环，long 预算 250min）
- **问题**：写者并存（ingest 写手、medium_tick 风扇/告警事务、slow_tick 三段、smart/volume 15m、downsampler、API CRUD、selftest），SQLite 单写者，靠 WAL + 3s busy 超时兜底；现有事务均短（executemany ≤50 行），3s 内通常够，超时即 P2-4 的丢批。selftest 长事务持连接可达数小时（占池 1 席；WAL 下不阻塞读写；rollback 路径丢全部事件，属业务既定策略）。未发现同一会话被多协程并发使用。
- **修复建议**：显式声明 pool_size/max_overflow；selftest 可改用独立 engine/短事务拆分。
- **优先级**：P2。

### P2-7 volumes.list_disks 与 gpu 缓存同款检查-执行竞态（重复 fork 代价低）

- **位置**：`backend/app/services/monitor/volumes.py:91`（60s 缓存检查）→ `:94-98`（await run_cmd lsblk，≤10s）→ `:131`（更新）；同模式 `gpu.py:415`（唯一调用方 medium_tick，实际无并发对手）
- **问题**：与 P1-2 同模式，但窗口内重复代价仅为 1-2 轮 lsblk fork（P1-2 是 N×smartctl×15s），并发调用方（slow_tick、smart_15m、selftest、/summary）撞车概率低。
- **修复建议**：与 P1-2 同一方案（in-flight 旗标），可一并实现。
- **优先级**：P2。
