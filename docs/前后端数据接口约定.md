## 1. 交互模型总则

### 1.1 部署形态与基址

| 形态 | 前端访问后端的完整基址 | 说明 |
|---|---|---|
| 后端直连 | `http://<nas>:8766` | 开发/调试；端口与 `api_prefix` 见 `backend/app/core/config.py`（`NASDECK_PORT=8766`、`api_prefix=/api/v1`） |
| fnOS 网关挂载 | `https://<nas>/cgi/ThirdParty/<pkg>/index.cgi` | 生产形态；`/api/v1/*` 必须挂在 `index.cgi/` 之下，子路径会被网关 404（前端 `API_BASE` 截取规则见 §7.1） |
| Vite 开发代理 | `http://localhost:5273`（dev server） | `vite.config.ts` 将 `/api` 代理到后端；**当前 target 指向 `127.0.0.1:9800`，与后端实际端口 8766 不一致，联调前需对齐** |

全部 REST 路径在本文中省略共同前缀，写法 `/monitor/realtime` 即 `GET {基址}/api/v1/monitor/realtime`。唯一例外是存活探针 `GET /health`，它**不在** `/api/v1` 下。

后端不托管前端静态资源（`templates/vue` 产物由网关/其他静态服务器托管）；交互调试文档：Swagger `/api/docs`、ReDoc `/api/redoc`、OpenAPI `/api/openapi.json`。

### 1.2 统一响应信封

**成功**（HTTP 200）：

```json
{ "code": 0, "message": "ok", "data": <业务数据>, "timestamp": 1759100000 }
```

**业务错误**（HTTP 4xx/5xx，由异常处理器产出）：

```json
{ "code": 1001, "message": "resource not found", "data": null }
```

实现细节（前端解析须知）：

- `timestamp` 为 Unix 秒；**错误信封没有 `timestamp` 字段**（`core/exceptions.py:_envelope` 只含 code/message/data）。
- 信封解包是前端职责：`apiJson` 现不解信封、直接透传整个 JSON，新数据层必须统一做 `code === 0 ? data : throw`（见 §7.3）。
- 未被异常处理器覆盖的 HTTP 错误（路由不存在 404、方法不允许 405 等）是 FastAPI 默认格式 `{"detail": ...}`，没有 code 字段——前端对非 0 code 与缺 code 两种情况都要兜底。
- 文件下载类接口（`/report/health/{filename}` 等）成功时**直接返回文件流**（`text/html` / `application/zip`），不走信封。

### 1.3 业务错误码表

| code | HTTP | 含义 | 典型触发 |
|---|---|---|---|
| 0 | 200 | 成功 | — |
| 1000 | 400 | 业务错误基类 | 兜底，正常不应出现 |
| 1001 | 404 | 资源不存在 | 控区/曲线/规则/报告文件不存在、自检无记录 |
| 1002 | 400 | 参数不合法 | 设备名/序列号不符合格式、curve 点校验失败、query 越界 |
| 1003 | 500 | 外部工具失败 | smartctl/storcli 缺失或执行失败 |
| 1004 | 403 | 权限拒绝 | `X-API-Key` 错误、kill 未带 confirm、白名单进程、受保护系统进程 |
| 1005 | 409 | 状态冲突 | 自检已在运行、置空别名 |
| 2000 | 422 | 请求校验失败 | body/query 不满足 Pydantic/Query 约束，message 带逐字段明细 |
| 5000 | 500 | 未处理服务器异常 | 兜底 |

### 1.4 鉴权

- 全部 `/api/v1/*` 路由要求请求头 `X-API-Key: <配置值>`；**未配置**（`NASDECK_API_KEY` 为空，默认）时不校验。
- 豁免：`GET /health`、Swagger/ReDoc/OpenAPI 三个文档端点、WebSocket（当前无鉴权，见 §4 注意事项）。
- 校验失败 → HTTP 403 + `{"code":1004, "message":"invalid or missing X-API-Key header"}`。

### 1.5 时间与单位约定

| 项 | 约定 | 备注 |
|---|---|---|
| 信封 `timestamp` | Unix 秒（整数） | — |
| 实时快照 `ts` | ISO8601 带 `Z`（如 `2026-09-29T08:00:00Z`） | — |
| 历史点 `ts` | **无时区后缀**的 ISO 字符串，值为 UTC（如 `2026-09-29T08:00:00`） | 前端须按 UTC 解析 |
| 事件/报告时间 | `fired_at`/`resolved_at` 带 `Z`；`assessed_at`/`started_at`/`completed_at` 带 `+00:00` | 两者等价，`new Date()` 均可解析 |
| 时长/年龄 | 字段名 `_s` 后缀，单位秒（`uptime_s`） | — |
| 温度 | `*_c` / `*_temp_c`，℃ 一位小数 | — |
| 速率 | `*_kbps`，KB/s 一位小数；部分附 `*_human` 可读串 | — |
| 容量 | `*_bytes` 整数字节；`*_human` 十进制可读串（GB/MB） | — |
| 百分比 | `*_percent` / `*_pct`，0–100 一位小数 | — |
| 枚举 | 全小写字符串（`health`、`grade`、`mode`、`severity`、`status`） | — |

### 1.6 写操作约定

- 变更一律 `POST`/`PUT`/`DELETE` + JSON body（`Content-Type: application/json`）；创建/更新成功返回 `{"id": <新id>}` 或回显关键字段，删除返回 `{"id": ..., "deleted": true}`。
- 危险操作显式确认：`DELETE /system/processes/{pid}?confirm=true`（缺 confirm → 1004）。
- DB 写入由请求级会话自动 commit（成功）/rollback（异常），前端无需幂等标记；自检、FCS 接管为后端进程内状态。

## 2. 公共数据类型字典

以下为 **data 载荷实际返回的字段**（与 `schemas/` 对齐，个别字段以实现为准并已标注）。箭头表示嵌套结构。

### 2.1 实时快照 RealtimeSnapshot（`/monitor/realtime`、WS `realtime` 事件）

| 字段 | 类型 | 说明 |
|---|---|---|
| `ts` | string | ISO8601 Z |
| `available` | boolean | 采集可用性（恒 true，保留位） |
| `cpu_percent` | float | 全机 CPU 占用 |
| `cpu_per_core` | float[] | 每核占用（0–100） |
| `cpu_freq_mhz` | float \| null | 当前主频 MHz |
| `cpu_freq_per_core` | (float \| null)[] | 每逻辑核当前频率 MHz；平台取不到的核为 null（可选字段，向后兼容） |
| `cpu_freq_max_mhz` | float \| null | 频率上限（scaling_max_freq），前端频率柱的归一化基准（可选字段） |
| `load` | float[] | 1/5/15 分钟负载（平台不支持时空数组） |
| `mem_used_mb` / `mem_total_mb` | float | 已使用 = MemTotal − MemAvailable（用户视角）/ 总大小 MB |
| `mem_percent` / `swap_percent` | float | 内存/交换分区占用 |
| `mem_available_mb` / `mem_buffers_mb` / `mem_cached_mb` / `mem_reserved_mb` | float \| null | 可用（MemAvailable）/ 缓冲（Buffers）/ 缓存（Cached）/ 系统保留。内存**全读 `/proc/meminfo`**（内核直接导出，零外部命令，Unraid 同口径），非 Linux 退回 psutil（缓冲/缓存为 null）；系统保留 = 已使用 − (缓冲+缓存) 的正差额，负值（被缓存覆盖）回 null。内存分量后端 **5s 采集缓存**（变化粒度粗，1s 无意义），其余快照字段仍 1s |
| `net` | object | `{ <iface>: { rx_kbps, tx_kbps, rx_human, tx_human, total_rx_mb, total_tx_mb } }`，不含 lo |
| `disk_io` | object | `{ read_kbps, write_kbps }` 全盘合计（无数据时 `{}`） |
| `process_count` / `uptime_s` | int | 进程数 / 开机秒数 |
| `gpu` | GpuRealtime \| null | `{ available, name, percent, vram_used_mb, vram_total_mb, temp_c, source }`。AMD 读 sysfs（gpu_busy_percent 等）、NVIDIA 调 nvidia-smi（只查需要字段）、Intel 经 intel_gpu_top -J 长驻进程（Render/3D busy；显存/温度无独立传感为 null），均 **5s 采样**；工具不在位时 available=false；无卡为 null |

> 规划中未实现：功耗字段（§6）。CPU 利用率来自 `/proc/stat` 两次采样差值、频率直读 `/sys` cpufreq、内存全读 `/proc/meminfo`——零外部命令（低占用架构，见各服务 docstring）。各域的数据源策略（proc 直读或 psutil 兜底）与外部工具在位性由**硬件采集策略决策层**（`services/hardware/policy.py`）在**启动时探测一次**并出进程级结论，采集代码只查结论不再各自探测；决策依据记入启动日志，`/system/env` 的工具清单与其共用同一注册表。

### 2.2 温度点 TemperatureItem（`/monitor/temperatures`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `key` | string | 唯一键 `{chip}:{label或序号}`，风扇控区 `sensor_key` 引用它 |
| `chip` | string | hwmon 芯片名（coretemp/nvme/drivetemp…） |
| `label` | string \| null | 传感器标签 |
| `celsius` | float | 温度 |
| `zone` | string | 归类：`cpu`/`nvme`/`disk`/`board`/`other`（控区 loop 取 `cpu`/`chassis`） |
| `grade` | string | 分级：`normal`(<60) / `warm`(≥60) / `hot`(≥75) / `critical`(≥85) |

### 2.3 历史响应 HistoryResponse（`/monitor/history`）

`{ points: HistoryPoint[], minutes: int, granularity: string }`

HistoryPoint：

| 字段 | 类型 | 说明 |
|---|---|---|
| `ts` | string | 无后缀 UTC ISO（§1.5） |
| `cpu_avg` / `cpu_max` | float \| null | CPU 占用 |
| `mem_avg_mb` | float \| null | 内存用量 MB |
| `net_avg_kbps` | float \| null | 收发合计速率 |
| `temp_max_c` | float \| null | 全机最高温 |
| `gpu_avg` | float \| null | **仅 raw 点**非空（GPU 实时已接入，medium_5s 采样回填） |
| `disk_read_kbps` / `disk_write_kbps` | float \| null | **仅 raw 点**；聚合点恒 null |
| `granularity` | string | 点级粒度：`raw` / `1m` / `10m` |

粒度规则：回看窗口整体落在 raw 保留期（默认 120 分钟）内用 `raw`；更早用 `1m`，超 30 天不返回。响应级 `granularity` 为本次返回的主粒度。

### 2.4 总览 Summary（`/monitor/summary`）

`{ cpu_percent, mem_percent, temp_max_c: float|null, uptime_s, disk_total: int, disk_health: { passed, warning, failing, unknown }, raid_degraded: int }`

### 2.5 磁盘 DiskItem（`/storage/disks`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `device` | string | 设备名**不带** `/dev/`（`sda`、`nvme0n1`） |
| `path` | string | `/dev/sda` |
| `serial` / `model` / `transport` | string \| null | 序列号/型号/接口（SATA/NVMe/USB…） |
| `size_bytes` / `size_human` | int / string | 容量 |
| `rotational` | boolean | 机械盘 true |
| `alias` | string \| null | 用户别名（按 serial 持久化） |
| `health` | string | `passed`/`failing`/`unknown`（SMART 慢采集 60s 缓存回填，`-n standby` 休眠盘无读数为 `unknown`） |
| `temp_c` / `power_on_hours` | float / int \| null | `temp_c` 来自 SMART 慢采集 60s 缓存（与盘温同轮，零额外 fork）；`power_on_hours` 暂无数据源恒 null |
| `partitions` | PartitionItem[] | **v2.3.5 增量**：lsblk children 递归平铺（拓扑树层级边），见下 |

**v2.3.5 PartitionItem**（`partitions[]` 元素）：`{ name(不带 /dev/，如 sda1/dm-0), size_bytes: int|null, fstype: string|null, mountpoint: string|null, type: "part"|"lvm"|"crypt"|… }`。LVM/加密层不做嵌套展开，按 lsblk TYPE 平铺标注。

**NVMe 健康匹配语义**：SMART 慢采集按控制器（`/dev/nvme0`）探测，`health`/`temp_c` 回填时 `nvme0n1` 形态盘名回退控制器名匹配——单命名空间 NAS 一一对应，多命名空间共享控制器健康。

### 2.6 SMART 报告 SmartReport（`/storage/disks/{device}/smart`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `device` | string | 不带前缀设备名 |
| `model` / `serial` / `firmware` | string \| null | — |
| `health` | string | `passed`/`warning`/`failing`/`unknown` |
| `temp_c` / `power_on_hours` / `power_cycles` | float / int / int \| null | — |
| `nvme_percent_used` / `nvme_media_errors` | int \| null | 仅 NVMe 盘非空 |
| `attributes` | Attribute[] | `{ id, name, value, worst, threshold, raw }`（SATA 全表；NVMe 为空数组） |
| `standby` | boolean | true=盘在休眠未唤醒，此时**其余字段只有 device/standby/health** |
| `assessed_at` | string \| null | 评估时间 |

错误：smartctl 缺失/失败 → 1003。

### 2.7 磁盘自检 SelfTestState（`/storage/self-tests`）

`{ device, type: "short"|"long"|"conveyance", status: "running"|"done"|"failed", started_at, completed_at: string|null, percent: int|null, result: string|null, error: string|null }`

`result` 到点后经 smartctl 自检日志判定：`completed`（无误）/ `aborted`（被中止）/ `failed`（完成但报错）/ `unknown`（无法确认，`error` 带说明）；`null` 仅 running 期间。

单盘互斥：同盘已有 running 自检再发起 → 1005。

### 2.8 阵列 RaidResponse（`/storage/raid`）

`{ available: boolean, hardware_raid: RaidVolumeItem[], software_raid: RaidVolumeItem[], storcli_error?: string, controller?: object|null, drives?: object[] }`

RaidVolumeItem：`{ source: "storcli"|"mdadm", controller, volume_id, name, level, size_bytes: int|null, state, healthy: boolean, details: object, members: RaidMemberItem[] }`（storcli 的 state 为 `Optl` 等；mdadm 的 state 为 `clean`/`degraded`/`unknown`）。storcli 缺失时 `available=false`，软 RAID 仍返回。

**v2.3.5 增量字段 `members`（阵列成员，只加不改名不删）**：

- storcli 形态：`{ slot("252:4"), sn, model, state, media, size_human, hotspare:"global"|"dedicated"|null, failed }`——PD 按 DG 编号与 VD join（storcli 拓扑表唯一可用关联）；专用热备 DG 同号一并挂入并以 `hotspare` 标记，全局热备（DG=`-`）不出现在任何 VD 的 members 中。DG 内承载多个 VD 时 PD 无法唯一归属，members 置空（宁缺勿错边）。
- mdadm 形态：`{ device("sda2"), index, faulty, spare, slot/sn/model/state/media/size_human/hotspare/failed 为 null/false }`——由 mdstat 成员段解析（`(F)`=faulty、`(S)`=spare、`(FS)` 同标）。
- **展示语义**：storcli VD 的块设备（如 /dev/sda）与 PD 之间无可靠 join（序列号不对应），VD 块设备会以直连盘形态出现在 `/storage/disks` 与拓扑树的直连分组中，属已知行为而非缺陷。

**v2.3.4 增量字段（Broadcom/LSI 阵列卡支持，只加不改名不删）**：

- `controller`：storcli 探测到的控制器信息（无卡/不可用时为 `null`）：`{ model, serial, fw_version, fw_package, bios_version, driver, pci, jbod_count, cachevault, cachevault_status, roc_temp_c, controller_temp_c, auto_copyback }`。CacheVault/BBU 为多格式兼容文本（如 `CVPM02 Optimal 25C`）；ROC 与 Controller 是两个物理温度传感器。
- `drives`：阵列卡侧物理盘数组：`{ slot("252:4"), state, dg, size("7.0T" 十进制换算), intf, media, model, sn, brand(中文品牌，可空), temp_c:int|null, media_err:int|null, failed, copyback_active, hotspare:"global"|"dedicated"|null }`。
- storcli 探测顺序：`NASDECK_STORCLI_PATH` → PATH → `backend/bin/storcli64`（随包分发）。`/storage/raid` 的 `available` 仅表示 storcli 硬 RAID 探测成功。
- **HBA 直通卡（IT 模式，如 LSI SAS2308）**：storcli 无硬 RAID 可报，此时 `controller` 为 `{ mode: "hba", model, note }`（经 lspci 只读检测），`available=false`、`storcli_error` 为直通说明文本；磁盘由内核直管，走 `software_raid`（mdstat）与 `/storage/disks`。

### 2.14 白名单 WhitelistItem、设置 SystemSetting、环境自检 EnvCheck

- WhitelistItem：`{ id, name, reason: string|null }`
- `GET /system/settings` data：`{ <key>: { value: any, description: string|null } }`；`value` 可为标量/object/array/null。
- EnvCheck（`GET /system/env`，安装期自举结果实时探测）：

```
{ python: { version, executable },
  config: { port, host, log_level, raw_keep_minutes, trim_auth },
  schemes: [ { domain, label, primary, source, fallback, ok, note } ], // 逐域采集方案（策略决策层启动判定）
  tools:   [ { name, desc, ok, path, install } ],   // install = 缺失时的安装包名（ok=true 为空串）
  drivers: [ { name, desc, loaded } ],              // /sys/module/<name> 探测，非 Linux 恒 false
  storcli: { ok, path, desc } }
```

`schemes` 为**本机实际采用的逐域数据采集方案**（cpu_util/net/power/temperature/fan/smart/soft_raid/hard_raid/gpu_<vendor>…）：`primary` 本机选定方案、`source` 数据源与实现要点、`fallback` 降级路径、`ok=false` 表示该域在本机不可用/降级（`note` 带原因或安装提示）。逐域结论同时逐行记入启动日志。

`config.log_level` 为**生效值**：NASDECK_LOG_LEVEL 显式配置优先，未配置时按版本通道缺省——`dev-` 前缀包 DEBUG（真机排查采集链路），正式包 INFO。

### 2.15 hwmon 通道 HwmonChannel（`/control/hwmon/channels`）

`{ chip, chip_path, pwm_channel: int, label: string|null, current_pwm_pct: float|null, current_rpm: int|null, pwm_enable: int|null, writable: boolean }`（非 Linux 恒空数组）

### 2.16 风扇控区 FanZoneItem（`/control/fans`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` / `name` | int / string | — |
| `loop` | string | 温度源回路：`cpu`/`chassis` |
| `hwmon_name` + `pwm_channel` | string + int | 定位唯一 pwm 通道（配 `fan_channel` 可选读转速） |
| `mode` | string | `auto`（交还内核）/ `curve`（温控曲线）/ `fixed`（定速） |
| `fixed_pwm` | int | 0–100，fixed 模式目标 |
| `curve_id` | int \| null | curve 模式引用 `/control/curves` |
| `enabled` | boolean | 停用控区不参与调速 |
| `sensor_key` | string \| null | 调速依据温度源（引用 TemperatureItem.key）；null/缺省 = 自动取 CPU 最高温。PUT 支持显式 null 清除回退自动 |
| `current_pwm_pct` / `current_rpm` / `sensor_temp_c` | float / int / float \| null | 实时反馈（通道消失时 null） |

### 2.17 温控曲线 CurveItem（`/control/curves`）

`{ id, name, points: [temp, pwm_pct][], hysteresis_c: float, ramp_per_tick: float }`

约束（违反 → 1002）：`points` ≥2 个点、pwm ∈ [0,100]、温度严格递增（后端会自动按温度排序）；`hysteresis_c` ∈ [0,10] 默认 2；`ramp_per_tick` ∈ [1,50] 默认 5。

### 2.18 FCS 状态 FcsStatus（`/control/fcs`）

`{ is_fnos: boolean, unit: string("pwm-fancontrol"), active: boolean|null(非Linux), taken_over: boolean, enabled_config: boolean }`

takeover/release 返回：`{ taken_over: boolean, reason?: string }` / `{ released: boolean, reason?: string }`。

### 2.19 告警规则 AlertRule / 渠道 AlertChannel / 事件 AlertEvent

- AlertRule：`{ id, name, metric, comparator, threshold: float, duration_ticks: int(1–1440，连续满足次数), severity, channel_ids: int[], enabled }`
  - `metric` ∈ `cpu_percent` `mem_percent` `temp_max` `disk_temp` `disk_failed` `raid_degraded`
  - `comparator` ∈ `>` `<` `>=` `<=` `==`；`severity` ∈ `info` `warning` `critical`
- AlertChannel：`{ id, name, type, enabled, config_masked: object }`；`type` ∈ `telegram` `bark` `email` `webhook`；**读接口只回脱敏后的 `config_masked`**，写入用 `config` 明文。
  - webhook config：`{ url: "http(s)://…" }`；通知以 JSON POST `{ source, title, body }` 发出，2xx 视为成功；url 非 http(s) 或缺失 → 1002。
- AlertEvent：`{ id, rule_id: int|null, rule_name, metric, value: float|null, threshold: float|null, severity, status: "firing"|"resolved", message: string|null, fired_at, resolved_at: string|null }`

### 2.20 报告 ReportResult（`/report/health`、`/report/diagnostic`）

`{ filename, url }`，`url` 为可直接下载的后端路径（如 `/api/v1/report/health/health_xxx.html`），前端拼上 API_BASE 即可。

## 4. WebSocket 实时推送

- 端点：`ws(s)://<基址>/api/v1/ws/realtime`（**完整路径含 `/api/v1`**，直接挂在应用根上）。
- 鉴权：**当前不走 X-API-Key**；经 fnOS 网关部署时 WebSocket 能否穿透 `/cgi/` 通道需真机验证，前端必须保留 HTTP 轮询降级（`GET /monitor/realtime` 本身就是 1s 级缓存，轮询可用）。

### 4.1 服务器 → 客户端（JSON 文本帧）

| `type` | `data` | 频率/时机 |
|---|---|---|
| `realtime` | RealtimeSnapshot | 连接建立即补发一条（缓存存在时）；之后每 1s |
| `fans` | FanZoneOutput[] | 每 5s，仅存在启用且非 auto 的控区时 |
| `alert` | `{ id, rule_name, status, severity, message }` | 告警触发/恢复时逐条 |
| `pong` | —（无 data 字段） | 收到 `ping` 后应答 |

FanZoneOutput（调速输出，与 `/control/fans` 的 FanZoneItem **不同**）：
`{ zone_id, name, loop, mode, target_pwm_pct: float, current_rpm: int|null, sensor_temp_c?: float, error?: string }`（写 pwm 失败或通道丢失时只有 `zone_id` + `error`）。

### 4.2 客户端 → 服务器

文本帧 `ping`（仅此一种）；建议前端 15–30s 发一次保活。

### 4.3 前端接入建议

- 断线自动重连：指数退避（1s 起、上限 30s）；重连后首条 `realtime` 即恢复数据，无需手工拉取。
- 同时保留轮询降级开关：WS 连续失败 N 次后切 `GET /monitor/realtime` 轮询，恢复后切回。
- 只在同一处（如 Pinia store）分发三种事件，页面订阅 store 而非直连 WS。

## 7. 前端对接约定

对应 `frontend/src/api/client.ts`（现状）与数据层重接（UNRAID 原型改造中）的目标形态。

### 7.1 基址与传输

- `API_BASE`：从 `location.pathname` 截 `index.cgi` 前缀（`/cgi/ThirdParty/<pkg>/index.cgi`），直连形态为空串。所有请求 = `API_BASE + /api/v1/...`。
- fetch 强制 `credentials: 'include'`（会话 cookie）、`cache: 'no-store'`（飞牛 WebView 缓存怪癖）、AbortController 超时（默认 30s，重接口单独放宽）。
- 错误归一为 `ApiError`（`status=0` 表示网络层失败）；网关会把 404 包装成 200，业务失败必须看信封 `code`，不能只看 HTTP 状态。
- 开发联调：vite dev server（5273）已代理 `/api`，**target 需改为后端实际端口 8766**。

### 7.2 WS URL

```ts
const wsUrl = (location.protocol === 'https:' ? 'wss:' : 'ws:') + '//' + location.host
            + API_BASE + '/api/v1/ws/realtime'
```

（网关形态下 host 与页面一致，路径带 `index.cgi` 前缀。）

### 7.3 信封解包（新数据层统一入口）

```ts
export async function apiData<T>(path: string, opts?: ApiJsonOptions): Promise<T> {
  const body = await apiJson<Envelope<T>>(path, opts)
  if (body.code !== 0) throw new ApiError(body.message, 200, body) // 业务错误也归一到 ApiError
  return body.data as T
}
```

`apiJson` 保留裸用能力（下载类接口、非信封响应）。

### 7.4 类型对齐

`frontend/src/types/api/` 旧类型（metrics/temps/docker 等 9 个文件）对应旧后端契约，随数据层重接逐域替换为 §2 字典的定义（每域一个 `*.types.ts`，命名与 `api/modules/` 对应）；替换完成前旧模块不得新增调用点。
