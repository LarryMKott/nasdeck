# nasdeck 功能健壮性原型设计（2026-10-25）

> **来源**：基于《REVIEW-2026-10-25.md》全项目评审结论，把"修 bug"之外的**功能级健壮性缺口**收敛成 6 个可独立采用的功能模块。
> **交付物**：本文档（行为规格）+ `prototype/nasdeck-robustness.html`（可交互 UI 原型，浏览器直开）。
> **状态口径**：每项标注 **[已实现]**（本轮 PR1–PR4+PR3，工作区已改、176 项测试全绿）或 **[待开发]**（本设计，待决策后实施）。
> **决策点**：文末"采用建议"给出推荐组合，由你勾选后我再开发。

## 设计原则（评审教训 → 设计约束）

评审里最刺眼的一类问题是"**说谎的界面**"：假刷新按钮、假阵列停止、假告警级别、假 kill 成功、冻结的 10m 历史。因此本设计遵循三条硬约束：

1. **状态必须可见**：任何降级/失败/演示数据，UI 与 API 都要如实呈现，不允许"看起来正常"。
2. **失败必须留痕**：后台任务死亡、通知发送失败、镜像不一致——必须进日志 + 指标 + 自检页三处之一。
3. **数据必须可解释**：历史图表标注缺口，聚合数据标注口径，演示数据全局横幅。

## 模块 A：风扇控区健康闭环

**对应评审**：P1-4/5/6（已修）、N4 通道防呆（已修）、N5 同名 chip 消歧、旧 P1-05 FCS 原子写。

### A1 调速失败可视化【待开发，S】

- **现状**：failsafe 状态已随 WS `fans` 事件推送（`failsafe: hold|full_speed`、`streak`、`error`），但 FanView 只显示转速/占空比，控区进入 failsafe 用户无感知（除非碰巧看 WS 数据）。
- **设计**：FanView 每个控区卡增加**状态条**：
  - 正常：绿色 "调速中"（当前档位来源：curve@62℃ / fixed 40% / auto）；
  - hold：琥珀 "传感器失联保持（2/3）" + 倒计时语义（再 N tick 全速）；
  - full_speed：红色 "失联保护全速" + 触发原因（sensor unavailable / curve missing）；
  - pwm write failed：红色 "写入失败"（通道只读/消失）。
- **后端补充**：`fan_manager` 内 20 条环形缓冲（zone_id、ts、error、failsafe），`GET /control/fans/events` 返回，FanView 底部"最近调速异常"表。
- **验收**：拔掉传感器键（改 sensor_key 为不存在值）5s 后 UI 出现 hold，15s 后 full_speed 红条。

### A2 restore_auto 失败可恢复【待开发，S】

- **现状**：交还内核失败已记 warning + API 响应带 warning（已修），但失败后无补救入口。
- **设计**：控区卡上失败状态出现"重试交还"按钮 → `POST /control/fans/{id}/restore-auto`（重跑 restore_auto 并回报结果）。
- **验收**：mock enable 只读时按钮出现，恢复可写后点击成功，状态条转绿。

### A3 FCS 状态原子写与损坏自检【待开发，S】

- **现状**：`fcs_safe_takeover` 状态文件 `write_text` 非原子，`load_state` 解析失败静默当"未接管"（旧 P1-05 未修）。
- **设计**：临时文件 + `os.replace` 原子替换；解析失败按**最坏情况**处理（`taken_over=True` 走对账告警路径），状态进自检页（模块 E）。
- **验收**：写入中途 kill 进程，重启后状态文件要么完整要么触发"按已接管对账"日志。

### A4 同名 chip 消歧【待开发，M】

- **现状**：FanZone 只存 `hwmon_name+pwm_channel`，双 nct67xx / 双 BMC 机器上写的是第一个同名 chip（N5）。
- **设计**：
  - `fan_zones` 加列 `chip_path TEXT NULL`（走模块 B4 的安全迁移）；
  - 通道扫描已返回 `chip_path`，创建控区时前端带上；`hwmon_driver` 的 find/read/write 全部优先按 chip_path 定位，回退按名字（兼容旧数据）；
  - FanView 控区卡显示完整绑定 `hwmon2 · pwm1`，通道列表按 chip 实例分组。
- **验收**：mock 两个同名 chip 目录，控区写入落在配置指定的那一个。

### A5 临界全速即时提示【待开发，S】

- **现状**：fixed 模式临界全速已实现（PR4），但用户不知道风扇为何突然 100%。
- **设计**：`fans` 输出条目带 `critical: true` 时，前端弹一次性 toast "CPU 91℃ 已超临界（85℃），控区『CPU 风扇』强制全速"。不新增告警规则类型（避免契约膨胀），复用 toast（模块 D2）。

## 模块 B：数据管线自检与自愈

**对应评审**：N8 ingest 无自愈、P0-4 残余、P0-5 整库重建、P1-2 已修。

### B1 ingest worker 自愈 + 管道指标【待开发，M】

- **现状**：`_write` 已包异常，但 `_run()` 意外死亡后 worker 永不重建、队列静默堆满丢弃（N8）。
- **设计**：
  - `add_done_callback`：task 异常结束时记 error 并 `start()` 重建（指数退避，上限 60s）；
  - 暴露 `ingest.stats()`：`{worker_restarts, queue_depth, queue_capacity, dropped_batches, last_write_ts}`；
  - `last_write_ts` 距今 > 30s 判"断流"，进自检页 + `/health` 仍保持轻量（不塞业务判断）。
- **验收**：测试里让 `_run` 抛异常，worker 自动重建且 restarts 计数 +1；UI 自检页显示断流红条。

### B2 降采样滞后指标【待开发，S】

- **现状**：完结桶修复后聚合正确，但"downsampler 是否在跑/落后多少"不可见。
- **设计**：`downsampler.stats()`：`{last_run_ts, completed_buckets_pending, last_purged_rows}`；已完结未聚合桶 > 3 判滞后（正常 ≤1 轮间隔）。进自检页。

### B3 历史图表缺口标注【待开发，M】

- **现状**：采集断流后图表直接连线跨过缺口，数据"看起来连续"——违反"数据可解释"原则。
- **设计**：
  - `GET /monitor/history` 响应增加 `gaps: [[start_ts, end_ts], ...]`（相邻点间隔 > 2×粒度即断口，上限 50 段）；
  - `ULineChart` 在缺口区间画**虚线 + 浅灰底带**，tooltip 标注"数据缺口（采集断流）"；
  - SysHistView 区间统计卡片旁标注缺口占比（如"缺口 4.2%"）。
- **验收**：手工删一段 raw 数据后查询，图表出现灰带且 stats 提示缺口。

### B4 DB 迁移安全化【待开发，M】

- **现状**：stale 列检测触发即 `drop_all` 整库重建，无备份无开关（P0-5 未修）；且检测白名单只覆盖 4 张表（N5 盲区）。
- **设计**（分两步走）：
  - **短期（本模块）**：重建前 `nasdeck.db → nasdeck.db.bak.<ts>`（失败则拒绝启动并明示路径）；`NASDECK_DB_ALLOW_REBUILD`（默认 `1` 保持现状兼容，文档建议生产关）；stale 检测改通用化——对每张业务表比对"模型列集 ⊆ 实际列集"，缺列即 stale；
  - **长期**：引入 Alembic（首版基线 = 当前 schema，之后加列走 migration），不在本模块范围。
- **验收**：给 `alert_rules` 加一列（白名单外表），启动时正确识别 stale → 备份文件存在 → 重建 → 自检页显示"发生过 schema 重建（备份于 …）"。

## 模块 C：通知可靠性

**对应评审**：P1-14 规则隔离、pending 无界（N7）、email 硬化（N6）、channel_ids 悬空（B 域 N-3）、SSRF 拒绝原因不透明。

### C1 规则隔离 + 发送重试【待开发，M】

- **现状**：规则循环无 per-rule try，单规则 flush 失败中断整轮且进程内 `_firing` 与 DB 状态错位（P1-14 残余）；`_drain` 单次失败即丢通知。
- **设计**：
  - 规则循环包 per-rule try/except，失败记 warning 继续下一规则；
  - `_pending` 条目带 `attempts` 计数，drain 失败且 attempts < 3 时重新入队（指数退避由 drain 周期天然形成）；3 次后放弃并在渠道卡片标"发送失败 ×N"（最近错误原因分类显示）；
  - `_pending` 上限 200，溢出丢弃并记一条本地 alert 事件（rule_name="nasdeck.notify", message="通知队列溢出丢弃 N 条"），保证可见性不静默。
- **验收**：mock 渠道 send 前两次 False 第三次 True，通知最终送达且 attempts=3 可查。

### C2 渠道测试反馈分类【待开发，S】

- **现状**：`POST /alert/channels/{id}/test` 只回布尔，SSRF 拒绝/超时/认证失败一个样。
- **设计**：send 返回 `bool` 改 `str | None`（None=成功，否则错误码）：`ssrf_rejected / timeout / auth_failed / dns_error / bad_response / disabled`；test 端点透传到响应；UI 测试按钮显示具体原因（如"被出网护栏拒绝：目标 192.168.1.4 属内网段"）。
- **契约**：`AlertTestOut { ok: bool, reason: str | null, detail: str | null }`。
- **验收**：配 webhook 指向 169.254.169.254，test 返回 `ssrf_rejected`，UI 红字显示。

### C3 email 硬化 + 引用校验【待开发，S】

- To/From 做 CRLF/控制字符清洗（与 title 同款）；`starttls(ssl.create_default_context())`；
- `channel_ids` 写入时校验全部存在（404/400）；删除渠道时若被规则引用，响应带 `referenced_by: [rule_id...]` 警告（不阻断删除，前端二次确认）。

## 模块 E：系统自检页（新视图）

**对应评审**：多处"失败不可见"的收敛出口。这是把 B/C/A 的指标变成用户可操作面板的壳。

### E1 后端 `GET /system/diagnostics`【待开发，M】

聚合返回分组清单（结构：`{groups: [{name, items: [{key, status: ok|warn|fail, detail, hint}]}]}`）：

| 分组 | 检查项（status 判定） |
|---|---|
| 数据管线 | ingest 断流（B1）、队列水位 >80%、downsampler 滞后（B2）、DB 最近重建记录（B4） |
| 风扇 | 受管控区当前 failsafe 状态、restore_auto 失败控区数、FCS 状态文件完整性（A3）、只读通道配置数 |
| 鉴权链 | trim_auth/proxy_token/api_key 配置组合是否安全（含 PR2c 的空 token 告警逻辑前端化）、升级镜像一致性（ui/port、ui/proxy_token vs 权威副本） |
| 采集工具 | smartctl / storcli / mdadm / sensors / docker CLI 可用性（已有散落检查的聚合） |
| 通知 | 各渠道最近一次发送结果与时间（C1）、_pending 水位 |

### E2 前端 SelfCheckView【待开发，S】

- 路由 `/selfcheck`（侧栏"自检"，管理菜单组）；进入即拉取 + "重新检查"按钮；
- 每项一行：状态灯（绿/琥珀/红）+ 检查名 + detail + **修复建议 hint**（如"在后端环境变量设置 NASDECK_PROXY_TOKEN 后重启"）；
- 顶部汇总徽标（正常 N 项 / 异常 M 项），异常时侧栏图标带红点；
- Navbar 铃铛下拉底部加"查看自检"入口（异常时引导）。

### E3 诊断包增强【待开发，S】

diagnostic zip 增加 `selfcheck.json`（E1 全量结果）；沿用 PR2b 的白名单脱敏管道。

## 与已完成修复的关系

本轮工作区已有改动（未提交）：PR1 发版止血、PR2 SSRF/脱敏/升级链、PR4 风扇安全（failsafe 体系/通道防呆/温度独立 try）、PR3 数据正确性（NVMe 口径/完结桶/gpu avg/Buffers）。本设计的 A1/A2/C2 直接消费这些修复产出的数据（failsafe 字段、warning 响应、错误码），是它们的"最后一公里展示层"。后端 176 项测试全绿作为共同基线。
